# WORKER-NOTES — the Borgarland relay

The Cloudflare Worker that files citizen reports (ábendingar) with Reykjavík,
records what was sent and what came back, and enforces what the city does not:
a usable coordinate and Reykjavík jurisdiction.

This file says how to run the thing, what is proven and what is stubbed, how
the dry-run gate works and why it cannot be bypassed by accident, and every
place the repo did not say and I had to choose. It was written from a build
done on 2026-08-21 against the repo at its state that day.

## Layout

```
wrangler.jsonc                Worker config. D1 database_id is a PLACEHOLDER.
schema.sql                    Reference schema with rationale.
migrations/0001_init.sql      The migration D1 applies (reports + addresses).
src/index.ts                  Worker entry: wires env into the app.
src/app.ts                    Routing + the create/read/outcome flows.
src/domain.ts                 Our vocabulary, the coordinate guard, description rules.
src/config.ts                 The dry-run gate (the one safety-critical file).
src/env.ts                    Env bindings: DB, CITY_SEND_KEY.
src/registry.ts               In-memory address index + nearest + display line.
src/jurisdiction.ts           SVFNR check: 0000 is Reykjavíkurborg, else refuse.
src/adapters/reykjavik.ts     THE adapter: city field names, slugs, URL. Only here.
src/db.ts                     D1 row insert/select/update for reports.
src/registry-loader.ts        D1 addresses table -> Registry, fail-closed.
scripts/refresh-registry.mjs  Downloads Staðfangaskrá (HMS) -> data/addresses.seed.sql.
data/reykjavik-form.json      COPY of the repo's canonical facts file (see below).
data/addresses.seed.sql       Generated by the refresh script. Gitignored.
tests/                        Vitest suite; city always stubbed.
```

## How to run

```bash
npm install
npm run typecheck      # tsc --noEmit
npm test               # vitest run
npm run check          # both
```

Bundle check (does not deploy, touches no Cloudflare account; it only bundles
locally — `--dry-run` exits before any API call):

```bash
npx wrangler deploy --dry-run --outdir dist
```

## What is proven

- **The relay works end to end** against a stubbed city and a real SQLite
  (Node's `node:sqlite`) behind a D1-shaped facade: the actual migration and
  the actual SQL the Worker runs are exercised.
- **Dry run is the default**: with no configuration, a report is validated,
  jurisdiction-checked, recorded as `dry_run = 1`, and the response carries the
  exact payload that would have gone over the wire — with zero city fetch
  calls (asserted).
- **The city POST happens exactly once per report in live mode**, with the
  city's field names, and the outcome (reference number from the done page, or
  rejection) is recorded in D1.
- **The 400 ambiguity**: a validation 400 (`Missing required fields` plus the
  re-rendered `category` hidden field) is classified `validation`; a 400
  without that envelope (unknown slug, changed route) is classified `route`.
  Both are recorded distinctly. The discriminator is ported exactly from
  `scripts/send-report.mjs`, including the note that the escaped regexes there
  are deliberate because the route answers React Router turbo-stream.
- **The coordinate guard**: missing, empty-string, `NaN`-as-text, Icelandic
  comma, non-numeric, and out-of-range coordinates are all rejected with
  `400 invalid-coordinate`; a literal `0,0` is refused by the jurisdiction
  check, not filed.
- **Jurisdiction**: a Kópavogur point is refused with `400 outside-reykjavik`
  naming the nearest address (`Hamraborg 3, 200 Kópavogur`, SVFNR 1000); a
  point with no registered address anywhere near it is refused; an unseeded
  registry answers `503 registry-not-loaded` (fail closed).
- **Category mapping comes from the facts file**, not hardcoded: `ruslafotur`
  → `specific` / `Ruslafötur` / `Ábending -> Ruslafötur`; `almenn-abending` →
  `general`, the only structural difference. An unknown or English slug is
  rejected with `400 unknown-category` before anything is sent.
- **The adapter isolation grep**: `ruslafotur` appears in `src/` nowhere (the
  adapter reads it from the facts JSON); `senda-abendingu` appears in `src/`
  only inside `src/adapters/reykjavik.ts`. The facts data file and the tests
  (which simulate the app and assert the adapter's mapping) contain the tokens
  legitimately.
- **Real data smoke** (run once, then removed from the suite because it needs
  the gitignored seed): 139,347 rows loaded from the current HMS export into
  the actual loader; SVFNR 0000 count 23,835 — exactly the number measured in
  the repo's facts file; Laugavegur 1's own coordinate → SVFNR 0; Kópavogur →
  1000; Akureyri → 6000.

## What is stubbed

- **The city, always.** `createApp` requires an injected `fetch` (deps.fetch);
  there is no code path from the app to `globalThis.fetch`. Every test passes
  a stub, and the suite additionally replaces `globalThis.fetch` with a
  thrower, so any accidental real network call fails the test loudly. Rule 1
  is structural, not a habit.
- **The D1 database** is a real SQLite behind a ~30-line facade implementing
  `prepare().bind().all()/run()`. The SQL is real.
- **The address registry in tests** is three fixture rows. The production
  loader (`registry-loader.ts`) is separately tested against fixture rows
  seeded into the real SQLite, and was once run against the real 139,347-row
  seed.
- **The production outbound fetch** (`index.ts` → `globalThis.fetch`) is never
  exercised by tests; that is what live mode does and it is gated (below).

Nothing in this build ever sent a request to reykjavik.is or any city host.
The only external host touched was HMS (the national address registry export,
`hmsstgsftpprodweu001.blob.core.windows.net`), by the refresh script and the
one-off smoke test. `scripts/send-report.mjs` in the repo root was not run.

## How dry run is enforced, and why it cannot be bypassed by accident

One gate, one place: `src/config.ts`.

```ts
isLiveSendEnabled(env)  // true only if env.CITY_SEND_KEY matches /^[A-Za-z0-9_-]{32,}$/
isDryRun(env)           // !isLiveSendEnabled(env)
```

`src/app.ts` calls `isDryRun(env)` at the top of the create-report flow. If dry
run: it validates, jurisdiction-checks, builds the would-be payload, inserts a
`dry_run = 1` row, and returns the payload — the city POST function is never
reached. If not dry run: it calls the adapter's `submitCityPayload`, which is
the only function in the tree that performs the POST.

The default is the safe path: doing nothing. `wrangler.jsonc` contains no
variable that flips it. Going live requires, deliberately:

1. Generating a strong token (≥32 chars of `[A-Za-z0-9_-]`, e.g.
   `openssl rand -hex 32`), and
2. Putting it as a **secret binding** with `wrangler secret put CITY_SEND_KEY`
   against a specific account and environment.

Why this cannot be bypassed by accident:

- **No committed variable.** A plain `DRY_RUN=false` var lives in
  `wrangler.jsonc`, which is committed and easy to flip or copy between
  environments. Secrets cannot live in committed config; they require the
  deliberate `wrangler secret put` command with account access.
- **Fail-closed on shape.** Any value that does not match the pattern —
  `"false"`, `"1"`, `""`, a typo, a copied short string — keeps the relay in
  dry run. You cannot typo your way to live.
- **No per-request opt-out.** A buggy or malicious app cannot force a live
  send; only the operator's secret can.
- **The tests pin the behavior.** Dry-run tests assert the injected city fetch
  is never called; the live test proves a secret of the right shape produces
  exactly one POST. A future change that moved the submit call above the gate
  would fail the dry-run tests.

## The API the app talks to

All bodies are JSON except `POST /api/reports`, which is multipart (photos).

- `POST /api/reports` — multipart fields: `category` (slug), `latitude`,
  `longitude`, `description` (≤2500), `email` (optional), `photo` (repeated,
  `image/jpeg` | `image/png` | `image/gif`). Returns `201 { report,
  cityPayload? }`. `cityPayload` is present only in dry run and is exactly what
  would have been sent (photo bytes summarized as name/type/size).
- `GET /api/reports/:id` — `200 { report }` or `404`.
- `POST /api/reports/:id/outcome` — JSON `{ "outcome": "fixed" | "not-fixed" }`.
  `200 { report }`, `400`, or `404`.

`report` fields: `id`, `category`, `latitude`, `longitude`, `description`,
`email`, `photoCount`, `photoBytes`, `dryRun`, `createdAt`, `sentAt` (null in
dry run and when the POST never delivered), `accepted` (null until the city
answered; `true` = HTTP 200), `cityStatus`, `cityReference` (the number from
`/done/{number}`, null if unknown), `rejection` (`validation` | `route` |
`error` | null), `outcome`, `outcomeAt`.

Error responses carry `{ "error": "<code>", ... }`:
`invalid-multipart` (400), `unknown-category` (400), `invalid-coordinate`
(400), `invalid-description` (400), `invalid-photo` (400),
`outside-reykjavik` (400, with `nearestAddress` and `svfnr`),
`jurisdiction-unknown` (400), `registry-not-loaded` (503), `city rejected the
report` / `city-unreachable` (502, with the recorded `report` embedded),
`not-found` (404), `method-not-allowed` (405), `internal` (500).

## Places the repo did not say and I had to choose

1. **Success-body reference extraction.** The repo documents the success
   signal only as a browser navigation to
   `/abendingar/senda-abendingu/{slug}/done/{number}` (established by the
   accidental real report 110474); the raw POST response body was never
   captured. The adapter extracts the number with `/done/(\d+)/` and records
   `cityReference`; a 2xx without a match is still treated as accepted, with a
   null reference. If the city's real success body differs, this is the first
   thing to re-check — with the probe, never with a real submission.
2. **HTTP status vocabulary.** Nothing in the repo says what the relay should
   return. Chosen: 201 created, 400 for client-fixable validation, 502 when
   the city rejects or is unreachable, 503 when the registry is unseeded, 404
   unknown id, 405 wrong method.
3. **Outcome vocabulary.** The repo says only "records the reporter later
   answering whether it was fixed". Chosen: `fixed` | `not-fixed`, stored on
   the reports row with `outcome_at`.
4. **The address line in the description.** AGENTS.md says "put the nearest
   registered address in the description we send", but not which side does it.
   The relay does — it already reverse-looked the coordinate — appending
   `\n\nNæsta skráða heimilisfang: <street, postcode city>`. If the line would
   push the description over 2500 it is dropped rather than the user's text
   truncated. The app should NOT append its own copy. (The line format
   "Laugavegur 1, 101 Reykjavík" reuses iceaddr-ts's postcode table.)
5. **Where the registry lives in the relay.** The repo says "the registry is a
   cache with a date" and is read via iceaddr-ts, but not where the Worker
   keeps it. Chosen: a D1 `addresses` table seeded by
   `scripts/refresh-registry.mjs` (which downloads the HMS export and emits
   `data/addresses.seed.sql`), loaded once per isolate, refreshed on a
   schedule. **The full national registry is used, not the Reykjavík subset**
   the app ships: a point in Kópavogur must find a Kópavogur address, or the
   jurisdiction check would wrongly pass it. The 0.25 MB "ships on the phone"
   figure is the app's.
6. **The dry-run gate shape.** The repo requires the safe default and a
   deliberate act to go live, but not the mechanism. Chosen: the
   `CITY_SEND_KEY` secret with a shape check, above.
7. **Photo handling.** The repo lists the city's upload limit as unknown and
   says finding it means uploading until something breaks. The relay forwards
   photo parts as-is (MIME-allowlisted from the facts file), records count +
   total bytes in D1, and stores no photo bytes. The API part name is `photo`;
   the adapter renames it to the city's `files`. No size/count cap is
   invented.
8. **`accepted` semantics.** Chosen: `true` when the city answered 200 (even
   if the reference number could not be read); `null` when the city never
   answered (dry run, or the POST failed before a response — distinguished by
   `dryRun` and `rejection`).
9. **Our API field names.** `latitude`/`longitude` rather than the city's
   `lat`/`lng`; `category` is the slug; `photo` for image parts. `type`,
   `summary` and the display name are never in the API — the adapter derives
   them from the facts file.
10. **Placeholder D1 id.** `wrangler.jsonc` carries `00000000-...`; the real
    id comes from `wrangler d1 create borgarland-relay --jurisdiction eu`
    (jurisdiction can only be set at creation — AGENTS.md) and must be pasted
    in at deploy time. No database was created and no Cloudflare account was
    touched.
11. **The facts file is a copy.** `data/reykjavik-form.json` here is a
    snapshot of the repo's canonical `data/reykjavik-form.json`. The two will
    drift; in the real repo the Worker should read the shared file (worker and
    data as siblings, e.g. `import facts from '../../data/reykjavik-form.json'`)
    or sync on a schedule. The daily `contract.yml` probe in the repo root is
    the fact-checking mechanism and should cover the adapter too.
12. **Types are hand-written.** `wrangler types` needs a real D1 id (account
    access), so `src/env.ts` declares the bindings by hand and typecheck runs
    plain `tsc --noEmit`.
13. **A network-failed send** is recorded as `rejection = 'error'` with
    `sent_at = null` (nothing was delivered) — the row is the measurement
    layer's record of the attempt, not a claim that it went out.
